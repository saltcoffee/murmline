# Murmur 0.1.0 开发文档

本文记录 0.1.0 的技术规格和验收要求。版本范围与交互示意见[产品文档](./产品文档.md)。主要数据流为「输入框 → 字数校验 → 创建仓库文件 → 更新时间线」。仓库文件是记录的持久化来源，视图中的列表可随时重建。

## 1. 工程起点与集成

采用 TypeScript、Obsidian 原生视图与 CSS。沿用官方示例的 esbuild 构建方式。插件清单取 `id: murmur`、`name: Murmur`、`version: 0.1.0`、`minAppVersion: 1.8.7`、`isDesktopOnly: false`。1.8.7 是读取宿主界面语言（`getLanguage()`）的 API 基线；桌面和移动端最低版本仍须实机验收。插件运行时使用 Obsidian Vault API 和 Web API，避免依赖 Node 文件系统。[官方示例工程](https://github.com/obsidianmd/obsidian-sample-plugin) · [官方 API 类型声明](https://raw.githubusercontent.com/obsidianmd/obsidian-api/master/obsidian.d.ts)

| 建议文件 | 职责 |
| --- | --- |
| `src/main.ts` | 注册视图、命令和侧栏图标，持有仓库访问模块；将入口统一到打开并聚焦时间线的函数 |
| `src/post.ts` | 正文换行规范化、计数与验证；排序键、本地日期键和标签。纯函数可脱离 Obsidian 验证 |
| `src/post-store.ts` | 生成并解析路径、读写 Markdown、维护候选记录索引、按游标读页、执行单条删除 |
| `src/timeline-view.ts` | `ItemView` 生命周期、输入框、分页、日期分隔、确认框以及加载或错误反馈 |
| `styles.css` | 样式限定在 `.murmur-view` 下，沿用主题变量以及宿主提供的按钮、菜单、弹窗样式 |

在 `Plugin.onload` 调用 `registerView('murmur-timeline', …)`，用 `addCommand` 注册 `capture-thought`（显示名「记录想法」），用 `addRibbonIcon` 注册同一入口。入口先查 `workspace.getLeavesOfType`，没有现有视图时取 `getLeaf('tab')` 并 `await leaf.setViewState(...)`；随后 `await workspace.revealLeaf(leaf)`，再滚至输入区并聚焦。连续打开时共用进行中的打开操作。注册阶段不抢焦点，不扫描仓库。[Obsidian Workspace 与 Plugin 接口](https://raw.githubusercontent.com/obsidianmd/obsidian-api/master/obsidian.d.ts)

## 2. 文件契约与数据边界

每条想法独占一个 Markdown 文件。新建和删除只涉及一条记录；即使两台设备离线写同一天的想法，也会生成各自的文件。代价是记录越多，仓库文件数越多。按 UTC 月份建目录以便枚举，以文件名的创建时间排序，复制、同步或恢复文件引起的修改时间变化不影响顺序。

**示例路径**（上海当地 2026-11-18 10:42）

```text
Murmur/2026-11/1794969720000_23a43b70-c2e4-4ad3-9131-181deb718d47.md
```

**文件内容**（第一行是格式标记，第二行起全部属于正文）

```markdown
<!-- murmur:v1 -->
书里读到的那句话，走到桥上才想明白。
```

| 数据 | 契约 |
| --- | --- |
| `id` | 记录键取完整文件名的主干，即 `<13 位毫秒时间戳>_<小写 UUID v4>`。两个内容相同的明确发布使用不同 UUID。 |
| `createdAt` | 从主干严格解析 UTC Unix 毫秒值，月份目录必须与该值的 UTC 年月一致。本地日期、星期及时分都是显示值。 |
| `text` | 创建时写入固定格式标记、一个 LF 和规范化后的全文。序列化器不追加结尾换行；解码器只移除标记行及其行结束符，保留正文首尾空白和用户输入的结尾换行。 |
| 文件归属 | 仅读取符合目录、文件名和版本标记的文件为记录。普通笔记、未知版本或无标记文件不参与展示或删除。识别到 v1 但正文无效时提示异常文件路径并保留原文件。 |

按需创建 `Murmur` 和当前月份目录。遇到同名普通文件占用目录位置时，报告具体路径，保留草稿。并发创建目录若报已存在，重新查询并确认是 `TFolder` 才继续。存储层只接受由自身构造或验证的记录路径；删除方法接收记录键，不能传入任意仓库路径或目录。[Vault 文件操作](https://docs.obsidian.md/Plugins/Vault)

## 3. 输入校验与提交

先把 CRLF 和单独 CR 统一成 LF。以 `Intl.Segmenter` 的 `granularity: 'grapheme'` 对全文分段，供计数器和提交校验共用；使用 `text.trim().length > 0` 仅判断是否全空白，写入值仍取规范化后的原文。目标 WebView 缺少 `Intl.Segmenter` 时使用随插件打包的扩展字素分段实现，运行同一组兼容性用例。原生 `textarea.maxLength` 按 UTF-16 码元截断，输入框应允许完整粘贴，并通过发布按钮与提交处理函数执行上限约束。[Unicode 字素分段规则](https://unicode.org/reports/tr29/)

| 输入样例 | 期望计数 | 提交 |
| --- | ---: | --- |
| 空串 / 两个空格 | 0 / 2 | 禁用 |
| `好`、`👨‍👩‍👧‍👦`、`🇨🇳`、`e` 加组合重音 U+0301 | 各 1 | 允许 |
| A、CRLF、B | 3 | 允许，存为两行 |
| 139 个「好」加一个家庭 emoji，再追加「！」 | 140 → 141 | 允许 → 禁用，全文留在输入框 |

1. 按钮和 ⌘/Ctrl + Enter 走同一提交函数。组合输入期间根据 composition 事件及 `event.isComposing` 跳过快捷键。提交前复验正文，立即锁定本次操作并暂时将输入框设为只读。
2. 为这次提交冻结正文、时间和 UUID。使用 `vault.create` 写完整文件。若结果不明，按原路径重读核对；同一提交的文件和内容已存在即视为成功。重试同一未改草稿复用提交键。若路径已被不同内容占用，保留双方内容并报告冲突。
3. 确认文件已保存后，按键更新索引，清空草稿，滚到顶部并聚焦。索引更新或列表刷新失败单独显示读取重试，不能把已保存内容作为新提交再写一次。写入失败解锁输入并保留原文；用户修改草稿后开始新的提交。宿主文件事件和提交回调都按键合并，避免新增两行。

## 4. 读取、分组与增量更新

- **首屏与翻页**。布局就绪且第一次打开时间线时，枚举专用目录下的月份和匹配文件名，建立轻量索引 `{id, createdAt, path}`。按时间戳降序，再按 UUID 的 ASCII 字典序降序，翻页和批量同步都使用同一顺序。启动只读路径元数据，打开视图后才按需用 `vault.cachedRead` 取本页正文。首屏和每次加载最多 50 条有效记录。
- **分页边界**。翻页从索引中的未读候选按上述顺序取记录，并记住第一个新增行的键供键盘聚焦。格式不匹配项直接跳过。单文件读取失败时按键放置可重试的错误行，将该键标为已检查并继续扫描，直至读到 50 条有效记录或候选耗尽。错误行不占这 50 条的名额，也不提供删除操作。单条重试只核对该文件，验证通过后原位替换，已消失或不属本插件则移除错误行。若候选枚举本身失败，保留已经提交到视图的行及尚未读取的键，从该处重试。候选耗尽时隐藏翻页按钮，单条重试入口仍可用。
- **日期与时间**。按设备本地年月日生成日期键，以两位 24 小时时分显示时间。用本地日历回退一天求「昨天」，非本年的标签补年份。相邻行日期键不同时插入分隔，分页接续时包含上一页末行。视图恢复前台及前台定时检查时，比较系统时区标识与本地日期。时区变化时，从原始时间戳重算所有已加载行（含错误行）的时分、日期键和分隔线，保留排序及未读候选；同一时区跨午夜只需更新「今天」「昨天」等标签。
- **同步与分页衔接**。用 `registerEvent` 订阅 Vault 的 create、modify、delete、rename。按旧、新路径更新索引，目录移动或移除时核对受影响的子项。新增候选先进入未读索引。每批变更按新到旧自动合入浏览范围内最多 50 条有效新增记录，其余保留到翻页。此前已到末尾（包括空时间线）时，同样按此上限补入。已显示记录保留原位置，即使新旧记录交错也能按未读键补齐。翻页期间到达的事件排队处理，按键去重。已加载记录修改时重读，移出范围或消失时移除对应行。
- **阅读位置**。更新行或重建分隔前，记下首个可见记录的键及其相对滚动容器上沿的偏移。更新后恢复该偏移；若该记录消失则优先选相邻的下一条。保留草稿和当前焦点。键盘触发翻页时，加载期间保留按钮及其焦点，成功后聚焦本页首个新增行的操作按钮；若用户已移开焦点，则保留新焦点。
- **异步与呈现**。同时只运行一次加载更早记录；页面刷新或视图关闭时使过期的读取结果失效。文件在读取中消失则重新核对索引，真实读取错误才给出重试。关闭视图时清理 DOM 监听、定时器及仓库订阅引用。正文用 `textContent` 输出，配合 `white-space: pre-wrap` 和 `overflow-wrap: anywhere`。包含 HTML、链接或嵌入语法的文本按原样显示。

首版按已浏览页数追加 DOM，索引内存随文件数线性增长。没有每日或总量配额，实际容量由设备与仓库决定。首轮性能验证分别记录索引构建、首批正文读取和首屏渲染耗时，以便区分文件数量和视图渲染带来的成本。

## 5. 删除与操作反馈

1. 从原生 `Menu` 打开 `Modal`，记录预览对应的键、原路径、文件对象和正文。确认框打开后接收该文件的 Vault 变更事件。检测到修改即使当前确认失效、禁用删除，并重新读取正文；有效的新预览显示后将焦点放回「取消」，等待用户再次确认。读取失败保留重试入口。文件移动、移除或失去有效标记时，结束确认并提示原因。父目录更名或移除同样会使受影响的确认失效。
2. 用户点击确认后锁定本次提交，记下当前预览版本并调用 `vault.read`。读取返回后，先确认弹窗仍打开、预览版本有效、原路径仍指向同一 `TFile`，再核对标记和正文。任何已检测到的变更都终止旧提交，即使更早发起的异步读取刚刚返回。内容更新走重新预览流程，通过全部检查后显示「删除中…」，锁定取消、Esc 和其他关闭入口，再调用 `app.fileManager.trashFile(file)`。关闭弹窗时释放监听并使进行中的预检失效。

`trashFile` 接受文件对象，未提供按预期版本删除的参数。从最后一次校验到宿主实际执行删除之间，其他设备的写入仍可能先落盘。确认保护覆盖插件已观察到的变更，跨设备读后删除仍有竞态；文件恢复能力取决于宿主删除设置。[FileManager.trashFile 官方声明](https://raw.githubusercontent.com/obsidianmd/obsidian-api/master/obsidian.d.ts)

删除成功后从索引及已显示列表移除该键，重算日期分隔，焦点优先移到下一条「更多」，其次移到上一条，列表清空则回到输入框。失败时保留原条目并显示可重试错误。预检期间可取消或按 Esc，焦点回到原「更多」。宿主删除开始后等待其结果，失败则恢复取消和重试。状态提示使用可读文本；字数超限和保存失败也应能被屏幕阅读器感知。

## 6. 实施顺序与验证

| 阶段 | 交付与检查点 | 对应产品验收 |
| --- | --- | --- |
| 1. 打通本地记录 | 在测试仓库加载插件，确认命令复用视图；先验证字素计数、文件往返与重复提交，再验证断网写入和重启读回 | A1、A2、A3、A6 |
| 2. 完成跨日阅读 | 构造同毫秒、跨午夜、跨年、夏令时及跨页同日记录；在加载后和翻页途中分别注入同步记录，核对排序、总数、游标和阅读位置；双向切换时区检查分隔数 | A4、A10、A12 |
| 3. 完成删除与错误处理 | 分别模拟单文件持续失败和目录枚举失败。在确认框打开时及最终读取尚未返回时注入修改、移动、删除事件，断言旧确认调用 `trashFile` 的次数为零；展示有效新正文并再次确认后才调用一次 | A5、A7、A9、A11 |
| 4. 发布前验收 | 在桌面浅色/深色主题和移动窄屏跑完整录入、回看、删除流程，检查输入法、焦点及列表触控，并执行产品表中的同步、故障及切换时区场景 | A1–A12 |

**构建与装载**。使用 Node.js 24，在项目根目录运行 `npm ci`、`npm run dev` 或 `npm run build`。把产出的 `main.js` 连同 `manifest.json`、`styles.css` 放入专用测试仓库的 `.obsidian/plugins/murmur/`，启用插件后按产品验收表逐项操作。测试记录注明宿主版本、系统、主题及时区。[官方示例的构建说明](https://github.com/obsidianmd/obsidian-sample-plugin)

**持续集成**。推送到 main 或提交拉取请求时，GitHub Actions 按锁文件安装依赖，运行 `npm run check`，依次检查 lint、测试、类型、构建及安装包元数据。成功后提供名为 `murmur` 的安装包，内含插件的三个安装文件。

**容量检查**。在测试仓库准备 10,000 条有效记录，含同日超过 50 条的样本。检查首次展示 50 行且只读本页所需正文；逐页浏览并收集记录键，与源文件集合比对，无漏项、无重复。继续发布第 10,001 条并重启读回。记录桌面与移动端实测耗时，此规模用于回归检查。

**数据检查**。将用户普通笔记、未知格式文件和 v1 异常文件混放在月份目录，再执行发布、加载及选中一条有效记录删除。逐文件比对，仅该次发布的目标文件新增、该次确认的目标文件移除。模拟「创建实际成功但回调报错」后重试，最终仍只有一个对应文件。

## 7. GitHub 首次推送与发版

目标仓库为 [saltcoffee/murmur](https://github.com/saltcoffee/murmur)。

### 首次推送 main

1. 在首次推送前，为该仓库设置 Actions secret `BRANCH_PROTECTION_TOKEN`。可使用仅授权给 `saltcoffee/murmur`、具有仓库 **Administration → Read and write** 权限的短期 fine-grained PAT。GitHub 默认工作流令牌无法创建仓库规则集。仓库需支持分支规则集。[GitHub 权限说明](https://docs.github.com/en/rest/repos/rules#create-a-repository-ruleset) · [规则集适用范围](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)
2. 将包含工作流和规则文件的首个提交推送到 `main` 后，**Protect main** 独立于构建运行。成功后，在 **Settings → Rules → Rulesets** 可看到生效的 **Murmur main pull requests**。规则禁止直接更新、强推及删除 `main`，无绕过名单。作者可自行合并 PR，规定的他人审批数为 0。
3. 如果仓库已存在、首次运行缺少凭据或需要重新核验，可在 **Actions → Protect main → Run workflow** 选择 `main`。工作流只创建缺失的专用规则集，已有同名规则集会接受校验。首次成功后可以撤销令牌并删除 secret，分支保护会继续生效。管理员也可直接在 GitHub 应用同一规则集。缺少管理令牌时，工作流使用默认只读令牌核验该规则集对 main 实际生效的三条规则。

保护从规则集创建成功时生效。首次推送与该时刻之间仍有短暂窗口，首次运行失败时应先解决错误并重跑。

### 发布版本

1. 通过 PR 更新 `manifest.json`、`package.json`、`package-lock.json` 和 `versions.json`，在根目录 `CHANGELOG.md` 添加对应的二级标题（例如 `## 0.1.0`）及版本说明。
2. 合并后在要发布的提交上创建并推送与清单版本完全一致的标签，例如 `0.1.0`。标签使用三段数字。工作流核对标签对应的提交与版本，提取该版本的变更记录，再运行 `npm ci` 和 `npm run check`。
3. **Release plugin** 先创建草稿，上传 `main.js`、`manifest.json`、`styles.css` 和同内容的 `style.css`，全部完成后才公开 Release。Obsidian 安装时使用 `styles.css`。上传中断可重新运行同一次工作流，已公开的版本重跑时只校验附件。[Obsidian 官方发版约定](https://github.com/obsidianmd/obsidian-sample-plugin#releasing-new-releases)
